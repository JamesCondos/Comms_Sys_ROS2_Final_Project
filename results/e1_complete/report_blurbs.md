## Implementation and experimental method

A reproducible ROS2-to-REST baseline was implemented using a dedicated ROS2 traffic package, a bounded FIFO gateway and a separate HTTP/1.1 REST server. The traffic comprised command, status, odometry and sensor messages, with configurable rates and payload sizes. One or two namespaced ROS2 robots published on separate class-specific topics; higher offered loads were generated by scaling the rates of the two robots while preserving the traffic proportions. Thus, the load labels denote robot-equivalents, not independent HTTP clients. The gateway used one persistent TCP connection and one outstanding request, with a capacity of 1,000 waiting messages and drop-tail overflow. Seven nominal loads from 32 to 2,048 messages/s were tested three times each, using a five-second warm-up and 60-second measurement window. Application retries and injected network faults were disabled. Reported latency values are averages of per-run statistics; repetitions are not pooled.

## Instrumentation and validation

Messages were traced using unique IDs, sequence numbers and a common host monotonic clock. Timestamps separated ROS2-to-gateway delay, FIFO waiting and the HTTP exchange. Queue occupancy, process CPU consumption, sender/handler busy fractions and deadline outcomes were also logged. The formal sweep accounted for 731,504 generated messages, including 345,066 FIFO drops, with 0 missing ROS2 messages, 0 HTTP request errors and 0 messages pending after the drain period. A separate five-minute two-robot test verified topic rates and persistent communication, with a packet capture covering every logged HTTP exchange. Configurations and source snapshots were saved so the results can be reproduced.

## Baseline scaling results

At the lowest load, the mean of the run-level p95 latencies was 4.54 ms. At 512 messages/s (16 robot-equivalents), completed throughput was 512.1 requests/s and mean run-level p95 latency was 4.42 ms. Increasing the offered load to 2048 messages/s (64 equivalents) produced a completed throughput of 547.5 requests/s, a mean run-level p95 latency of 4689.89 ms and a time-averaged queue occupancy of 999.7 messages. At this load, 73.27% of generated messages were discarded at FIFO admission. The rising delay and queue occupancy, together with throughput falling below offered load, provide evidence of overload in the measured architecture.

## Interpreting the bottleneck

At the highest load, the gateway sender was occupied for 99.5% of the measurement interval, while the server POST handler was occupied for 39.3%. Gateway and server CPU consumption averaged 114.2% and 14.7% of one logical CPU, respectively. Averaging each run's mean delays gave 4175.88 ms of queue waiting and 3.98 ms for the HTTP exchange. These measurements implicate the serial gateway/client service path and its queue; they do not establish that the REST server or a physical network link exhausted its capacity. Consequently, adding server workers alone cannot be assumed to resolve this bottleneck.

## Deadline performance

Illustrative project deadline targets were fixed before the final sweep: 100 ms for command, 200 ms for status, 100 ms for odometry and 1,000 ms for sensor messages. A deadline failure included a late response or any message that did not complete, including FIFO overflow. At the highest load, command p95 latency reached 4676.28 ms and 100.00% of generated commands missed their target. These results show the extent to which FIFO fails to protect critical traffic under this stress condition. The deadline values are experimental design choices, not safety requirements.

## Repeat variability

At the highest load, completed throughput ranged from 139.1 to 1309.0 requests/s across the three repetitions, while p95 latency ranged from 851.40 to 7649.29 ms. CPU time per message increased across multiple processes later in the sweep, with a marked change during the first 32-equivalent run. This indicates variation in shared-host execution performance; the measurements do not establish its cause. All runs were retained. The results support a no-overflow reference at 16 equivalents and an overload stress condition at 64 equivalents, but do not support a single stable service-capacity estimate.

## Limitations and scope

All processes ran on a shared Ubuntu WSL2 host using loopback. The results therefore describe this implementation and machine, rather than a physical distributed-robot deployment. Periodic rate-scaled traffic was used, so an M/M/1 model is not assumed. Latency statistics include only successful messages generated during measurement, including completions during the bounded drain; deadline-failure ratios include unsuccessful messages. Throughput counts completions inside the measurement window. Figure points are means of three run-level statistics and error bars show their minimum and maximum, not confidence intervals. Sparse command samples at low load limit p99 precision. The earlier single-topic baseline is retained as preliminary data and is not pooled with this final dataset.
